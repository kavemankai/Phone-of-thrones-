# Shieldwall v0.9 — Playtest, regression and handover

Status: **candidate, not verified on-device**. Developed from the v0.8 branch head `e7ab545b389cd052305c4bb9d3d1c8e30a81d499`. No imported art assets, networking or monetisation changes. Default behaviour remains v0.8 unless players opt into a trial.

## Implemented in this branch

1. Defensive input priority: process immediately pressed dodge/block and newly released block before enemy strike collision. Enemy strike still precedes hero attack resolution; simultaneous killing blow is still defeat.
2. A/B controls: HOLD = current tap/hold scheme, with attack on release; SPLIT = instant LIGHT on button-down and dedicated HEAVY button on button-down. Desktop J still uses tap/hold; the on-phone option is what is being evaluated.
3. A/B defence: ALL-ROUND = original 360-degree guard, 0.40/0.32 s shield/bare parry and original recoil. DIRECTIONAL = 140/110 degrees, 0.30/0.23 s parry windows, 55% of existing weapon-specific block-stun duration. Other damage and guard costs unchanged. These are hypotheses, not final balance.
4. Readability: stronger locked telegraph outlines, grunts/captain ground identity rings, captain overhead name, hero PARRY/BLOCK/BROKEN/HIT flashes, HUD labels for HOLD/SPLIT and 360/DIR.
5. Regression scenarios added to `tests/run_tests.gd`: same-frame dodge, same-frame block, guard release before strike, no-defence hit, default restoration, alternative guard values, instant light and heavy.

Use Godot 4.6.2-stable with Android export templates and SDK as documented in the README.

```bash

godot --headless --path . --script tests/run_tests.gd
godot --headless --path . --export-debug Android build/shieldwall-debug.apk
```

Record exit codes, actual pass/fail count and any warnings. Do **not** reuse the 450-check result for 0.8 as if it were 0.9. No such validation has been performed for v0.9 in this environment.

## Physical Android A/B matrix

Use the same weapon (Sword + Shield), encounter (1 Enemy first, then 3 + Captain), device and tester for each comparison. Play three fights per setting without changing any other tuning values.

| Trial | Attack input | Guard | Key question |
| --- | --- | --- | --- |
| A (baseline) | HOLD | ALL-ROUND | Does the original feel best? |
| B | SPLIT | ALL-ROUND | Is light attack more responsive? Does fourth button crowd the thumb? |
| C | HOLD | DIRECTIONAL | Do positioning and flanking finally matter? Is parry still fair? |
| D | SPLIT | DIRECTIONAL | Is this better overall, or too much button complexity? |

For each run, capture: win/loss, fight length, accidental heavy attacks, missed dodges, unclear incoming hits, thumb repositioning, input failures, FPS (target 60, minimum 30), and whether the tester immediately chooses Retry. Prefer a short screen recording with touch overlay. Test on the smallest intended Android display, including navigation bar/notch safe areas. Test the extra HEAVY button with two-thumb play.

## Acceptance gates

- No game-breaking errors on import, in automated checks, on Android launch, after app pause/resume, or over ten retries.
- Dodge/block registered before a strike in the same simulation step. Attack commitment and no-phantom-guard behaviour remain correct.
- No overlap or unreachable buttons in either mode on the target device.
- Most observed hits are explainable; locked wedges match damage regions.
- Playtest results select a preferred input scheme and guard scheme. Do not claim a winner before actual observation.

## Limitations and next steps

Godot headless checks have executed in GitHub Actions. No physical Android gameplay test, performance benchmark or audio evaluation occurred during this implementation. This is still procedural placeholder art, not a content milestone. The diamond arena may remain too small in portrait; do not expand to army combat until the readability and control gates pass. The 0.8 baseline test report is retained unchanged as historical evidence.
